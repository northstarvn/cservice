# CService Backend — Code Map (Newick) Governance

Companion to [`CODE_MAP.newick`](CODE_MAP.newick). That file is a single-line,
strictly well-formed Newick tree that reflects the **entire backend logic** at
business-surface granularity. This document explains how to read it and how to
keep it in sync as the backend evolves.

## Revision Control

- Revision ID: `r6`
- Scope: backend logic only (`fastapi/app/**`); frontend and requirement
  artifacts are out of scope, matching `ARCHITECTURE_CONCEPT_MAP.md`
- Purpose: a machine-readable, diff-friendly map that mirrors module
  structure, ownership, and the business surfaces each module exposes
- Stop rule: leaves describe *business logic surfaces*, never every endpoint or
  helper; if a leaf would need route-level enumeration to be meaningful, the
  underlying code is probably overgrown (a signal for `efficiency_audit`)
- Resume rule: update the tree whenever a module gains a *new business
  surface* (new router domain, new service rule engine, new schema family, new
  infra capability), and bump the revision below

## Reading the Tree

Newick is a nested-parenthesis notation: `(child1,child2,child3)label`.
Leaves are business surfaces; internal node labels name layers (root:
`cservice_backend`, then `infra`, `models`, `routers`, `services`,
`schemas`).

| Layer | What its leaves mean |
|---|---|
| `infra` | startup/metadata (`main`), database plumbing (`db`), auth primitives (`security`), auth dependencies (`auth_deps`), localization, multi-tenant routing + partition lifecycle (`multi_tenant`), zero-trust crypto (`zero_trust`), event pipeline (`event_pipeline`), decision intelligence (`decision_intelligence`), business-rule hyper-flexibility (`business_rules`) |
| `models` | isolated polymorphic base models (`model_bases`) plus persisted domain entities (identity, booking lifecycle, chat signals, retention, policy, topics, communication, payments, points, audit trail, security events, preferences and consent) |
| `routers` | public API domains and their grouped surfaces (`users`, `bookings`, `chat`, `topics`, `complaints`, `audit`) |
| `services` | the rule engines — own the business logic (scoring, retention, loyalty, activity trees, communication strategy, payments, points, audit trail, and the customer-facing visibility layer) |
| `schemas` | contract families (`schemas_core`, `schemas_chat`, `schemas_audit`) |

Rules of thumb:

- A leaf appearing under `services` means the logic lives in that service, not
  in the router (thin-adapter convention).
- A leaf appearing under a router means it is a *distinct public surface*
  (e.g. `arrears_payments` under `chat` because those routes are exposed by
  the chat router).
- Entities that are only data carriers (no business rules) appear only under
  `models`, never duplicated elsewhere.

## Maintenance Rules

1. **Add a leaf** when a module exposes a genuinely new business surface
   (new router domain, new service engine, new persisted domain entity).
2. **Move a leaf** when ownership changes (e.g. topic intelligence moves from
   the chat router into a dedicated router — update the tree the same commit).
3. **Never enumerate endpoints as leaves.** If a router gains a fifth
   sub-surface under the same domain (e.g. another `/chat/admin/*` report),
   fold it into the existing leaf instead of adding a row.
4. **Keep the single-line format in `CODE_MAP.newick`.** Do not hand-edit it;
   regenerate via `python3 scripts/build_code_map.py` (nested tuples →
   serialize → parse-validate; prints `leaves=N internal_nodes=M`) and re-run
   the validation. `CODE_MAP.md` may keep a readable multi-line rendering, but
   the Newick file is the source of truth.
5. **Update `/meta/` surfaces in the same commit**: when the map gains a leaf,
   the corresponding `main.py` ecosystem/features/scoring-catalog entries
   should already reflect it — the map documents what the backend already says.
6. **Bump the revision** on structural changes only (new layer, new top-level
   domain). Leaf-level additions are recorded in the log without a bump.

## Revision Log

### r6 — Complaints: the case spine, the escalation engine, and decision support (2026-09-30)

Four new business surfaces, which is the resume rule firing on all three of its
triggers at once (new router domain, new service rule engine, new schema
family).

**`routers/complaints.py` (new router domain).** A case is not a chat message:
it has an identity that outlives the session that produced it, is quoted over
the phone days later, and has stakeholders beyond the person who typed it.
Grouped as `case`, `case_list`, `case_detail`, `note`, `withdraw`, `reopen`,
`acknowledge`, `resolve`, `close`, `decision_support`, `apply`,
`customer_visibility`, `queue`, `sla_report`, `auto_escalation_sweep`,
`decision_audit`, `governance` — 17 leaves for 18 routes, because rule 3
forbids enumerating endpoints.

**`services/complaints.py` (new service rule engine).** Config tables plus pure
evaluators that return a verdict and never raise, following the seven-part
skeleton every other surface in this backend uses. Nineteen leaves, one per
decision-support surface: `case_lifecycle`, `case_timeline`, `case_ownership`,
`escalation_triggers`, `escalation_guards`, `escalation_decision`,
`authority_floor`, `routing`, `sla_matrix`, `regulatory_deadline`,
`decision_feeds`, `decision_dossier`, `precedent_retrieval`,
`decision_history`, `auto_escalation_sweep`, `sla_report`, `admin_rollup`,
`validation`, `catalog`.

**`schemas/chat.py` (new contract family).** `complaint_case`,
`complaint_event`, `complaint_decision`, `complaint_dossier`,
`complaint_precedent`, `complaint_decision_support`, `complaint_admin`,
`complaint_catalog`.

**`models.py` + one migration.** `complaint_cases` (mutable — a case is a live
state machine), `complaint_events` (append-only — the timeline),
`complaint_decisions` (append-only — the operator's reasoning, with

### r6 addendum — complaint learning: `services/complaint_learning`, `routers/complaints` (2026-09-30)

A new service module and twelve new routes under the existing complaints router.
No new layer and no new top-level domain — `complaint_learning` is complaint
machinery, and it is deliberately *not* its own domain — so per maintenance rule 6
the revision stays **`r6`**; the tree grew **704 → 739 leaves** (65 → 66 internal
nodes).

**`services/complaint_learning.py` (new service — 24 leaves, one node).** Three
mechanisms that `services/complaints.py` structurally could not contain, each of
which is a boundary rather than a feature:

*System-originated complaints* (`system_detectors`, `detector_gates`,
`system_raise`). A complaint could only start because a customer asked for one.
Six detectors now watch live cases and can open one attributed to a customer who
never complained. Three guards make unattended operation defensible, and all
three are per-detector config rather than code: the detector's own `confidence`
against its own `min_confidence`, a per-`(detector, customer)` `cooldown_hours`,
and `dedupe_category`. A fourth, `SYSTEM_RAISE_CAP`, is per-call and is the guard
against one corrupt snapshot becoming one case per customer.

*Learned contribution weights* (`loyalty_objective`, `loyalty_signals`,
`learning_parameters`, `weight_authority`, `signal_readers`,
`contribution_scoring`, `weight_update`, `confidence`, `weight_report`,
`loyalty_facts`, `learning_pass`, `weight_store`). Seventeen signals, each with a
direction relative to a retention objective and a configured prior, whose weights
move on observed loyalty outcomes. Bounded, decayed toward the prior, persisted
in a table rather than module state, and versioned.

*Stacked-complaint clustering* (`cluster_detection`, `cluster_thresholds`,
`proposal_rendering`, `proposal_store`, `proposal_publishing`,
`blockages_render`). Five cluster rules, each multi-axis, producing suggestions
shaped like `efficiency_audit.EnhancementProposal` that are registered on the
release ladder at `l0_draft`.

**The three decisions this addendum exists to record.**

*"Loyalty" is retention and habitual return, not engagement volume.* The
objective is measurable retention — churn risk, reactivation, repeat booking,
points accrual. It is explicitly **not** time-on-service or contact frequency,
and `objective.not_optimised` in the catalog says so in as many words. A
complaint system that rewards more contact is inverting its own purpose: the
customer contacting us is the failure signal, and treating it as the goal makes
the angriest customer the most valued one.

*Learned weights are advisory, and the boundary is structural rather than
documented.* `LEARNED_WEIGHT_AUTHORITY` is a dict, and a dict does not stop
anyone from editing it — so the guarantee is that no learned number ever enters
the `context` dict that the escalation triggers are evaluated against. A weight
reaches the dossier only as the eleventh feed, `loyalty_contribution`, marked
`required: false`. The escalation path has no way to see a weight, so it cannot
move a tier even by accident. `validate_complaint_learning` errors if any of the
three `False` authority flags is ever flipped, and a test pins that the trigger
context contains no weight-bearing key at all.

*Suggestions enter the release ladder, not `BLOCKAGES.md`.* The ladder's
`l0_draft` is described in its own config as "written but unexamined... where
every kaizen change starts and where it is safe to be wrong", which is exactly
what an unreviewed complaint-derived idea is. `BLOCKAGES.md` is hand-authored
governance prose containing a keep-as-is list and a machine-sync guardrail; a
generated section inside it would grow without bound and would invert the
document's authority. So the module **renders** a pasteable section and reports a
diff that can only ever propose additions — `render_blockages_section` and
`diff_against_rendered` are pure, and there is no write path to the file anywhere
in the module. The `GET /complaints/admin/learning/blockages` response carries
`writes: false`.

**Three schema tables, one migration** (`0008_complaint_learning`, chained from
`0007_sync_remaining_schema`): `complaint_signal_weights` (mutable, the current
belief), `complaint_signal_observations` (append-only, the learning set, with
`weight_snapshot` freezing what the operator was shown), and
`complaint_improvement_proposals` (durable suggestions with a deterministic
`proposal_id` derived from the cluster key rather than the evidence, so a
dismissed suggestion does not reappear on the next sweep).

**Two pre-existing defects found on the way, both in code this work touched.**

`ReleaseCandidate.pair()` raised `AttributeError` on every call: it passed the
dataclass to `split_version_pair`, which reads with `.get`. That is the method
the rollback path uses to name the versions it must return to, so a rollback that
tried to resolve its own version pair could not.

`CHAIN` in `tests/test_migration_chain.py` is hand-maintained and nothing
compared it to the directory. The first version of this migration applied
cleanly in isolation and reported itself verified, while being absent from the
list the chain actually runs — so all three tables would have shipped with no
migration. `test_the_chain_lists_every_migration_file_on_disk` now closes that.

### r6 fourth addendum — mail delivery and the token exchange (2026-10-01)

Leaf-level again, so per maintenance rule 6 the revision stays **`r6`**; the tree
grew **801 → 808 leaves** (72 → 73 internal nodes). Closes the two pendings the
sign-in work left open.

**`services/mail`** (6 leaves, one node). The delivery half of the one-time code,
which was previously a complete credential with nothing to deliver it.
**`delivery_boundary`** is the leaf that matters: three transports (smtp, file,
simulated) behind one interface, with the load-bearing distinction being
*accepted* versus *delivered*. A simulated send is accepted and not delivered,
and the endpoint response says so — without that split, a deployment with no
mail server reports "check your email" forever while the code is generated,
hashed, stored and dropped, which presents as a mail outage and is debugged in
the wrong place. **`simulated_outbox`** is a leaf rather than an implementation
detail because it holds *plaintext codes*: bounded, in-memory, and reachable
only in the non-delivering transport.

The uniformity guarantee is what makes `delivered` and `delivery_transport`
publishable at all. They describe the deployment, not the account, so they are
identical for a real username and an unknown one — pinned by a test that compares
the two response bodies directly.

**`services/storage_providers/token_exchange`** (1 leaf). The authorization-code
exchange with the stored PKCE verifier. Its notable property is what it refuses
to do: with no client credentials it returns a reason naming the two env vars,
and with no transport it reports that the request is composed and ready. Neither
path fabricates a token, because a fabricated token makes a connection look live
while every file operation behind it fails. `ExchangeResult.to_dict()` excludes
both plaintext tokens, since that dict is what gets logged and written to a row's
`last_error`.

`/meta/ecosystem` now reports `can_complete` for storage — credentials *and*
transport *and* redirect URI — because `token_exchange_implemented: true` reads
as "this works" on a deployment that will still hold at `pending`.

### r6 second addendum — completeness grading and the one-command sweep (2026-09-30)

Leaf-level again, so per maintenance rule 6 the revision stays **`r6`**; the tree
grew **704 → 763 leaves** (65 → 68 internal nodes).

**`infra/kaizen/capability_audit`** (11 leaves). The second axis to the flow
simulation. Six graded states — `absent`, `declared_only`, `stub`, `partial`,
`untested`, `complete` — rather than a boolean, because a gap, a defect and a
part nobody has tested want different responses from the same person on the same
day, and "we found nothing wrong" is not the same sentence as "we looked at
nothing".

Two rules make it trustworthy rather than merely useful:

* **Absence is evidence, never a caught exception.** A probe that raised is
  equally consistent with a typo, a renamed argument and a regression. `unknown`
  never degrades to `absent`, and a probe is deferred only when its target
  positively failed to resolve.
* **What counts as fatal depends on the maturity rung.** A defect blocks at
  every level; a gap blocks from `l3_canary`; an unexercised part blocks only at
  `l4_live`, because canarying an unmeasured part is how you measure it and
  shipping one is not. An immature backend therefore passes at `l0_draft`,
  which is the requirement — "not built yet" is this project's starting state
  and must not block the first commit of every feature.

**`infra/kaizen/kaizen_sweep`** (11 leaves). One entry point for all three
subsystems and the background worker, so the CLI and the timer run the same
function. Three exit codes, because "nothing wrong" and "I could not tell" must
never return the same number — and a gate that was *never measured* is not a
failed gate, or the sweep would say "no" on every developer checkout and be
learned to be ignored.

**`routers/kaizen`**: three leaves — `completeness_report`, `sweep_status`,
`sweep_now`. The sweep endpoint refuses to append to the log, because an
endpoint a dashboard can poll should not be able to write it.

- **What became config** — three tables kept deliberately separate, because
  they carry different kinds of truth:
